可以，而且我认为现在正是 `go_ana` 做减法的合适阶段。

目前项目已经有相当多的骨架：LearningEvent、LearningPriority、CandidateAssessment、错题、mastery、Human SL、LLM、error chain、learning profile、主动复盘 UI 等。 如果继续沿着“每个能力都做一个入口、一个页面、一个图表”的路走，很容易得到一个功能丰富但每天只想点两三个按钮的软件。人类开发软件经常把“能做”误认为“应该露出来”，然后菜单就开始繁殖。

我的建议是把下一阶段定义成：

# go_ana「减法重构」

目标不是减少能力，而是：

> **减少用户需要理解、选择和操作的功能数量，同时保留后台分析能力。**

最终把整个产品压缩到一条非常明确的主循环：

**导入棋谱 → 系统找出最值得学的 5 个问题 → 用户重下 → 理解问题 → 自动进入复习 → 下一盘验证是否复发。**

这正好也是你之前确定的最终产品逻辑。

# 一、先看主流产品真正值得学的是什么

不要照抄功能表，要看它们**刻意把什么放在用户面前**。

| 产品        | 当前主要价值                     | 值得 go_ana 学 | 不应该学              |
| --------- | -------------------------- | ----------- | ----------------- |
| AI Sensei | 找关键问题 → 理解 → 保存 → Training | 极短学习闭环      | 社区、AI 对弈等扩张方向     |
| KaTrain   | Point Loss、问题手、立即反馈、Retry  | 复盘极直接，指标克制  | 大量专业参数直接暴露        |
| OGS       | 对局结束后直接进入 AI Review        | 分析成为自然后续动作  | 把自己建设成综合对弈平台      |
| 星阵        | 强分析能力 + 专业研究               | 专业能力放到深层    | 默认把研究能力全部扔给普通学习用户 |
| 涨棋网       | 下棋、分析、做题、报告、成长             | 学习结果和成长反馈   | “什么都有”的产品边界       |

AI Sensei 现在公开强调的训练循环就是 **Play → Review → Remember → Train → Play again**，训练内容直接来自本人实战错误；它的首页定位也明确强调“快速找到错误”“一眼看到重要问题”。([AI Sensei][1])

KaTrain 的核心介绍直到现在仍然非常集中：找出目数损失最大的棋、错误即时反馈、允许重试、自动生成聚焦最大错误的 SGF Review。([GitHub][2])

这两个恰好是 `go_ana` 最应该学习的对象。

星阵与涨棋网则提供另一种参照。星阵拥有更重的分析和研究能力，而且 2026 年还在尝试用自然语言解释 AI 数值背后的原因；涨棋网则已经扩展到 AI 分析、死活、人机、报告和成长曲线等一整套综合训练产品。([星阵围棋][3])

所以结论不是：

> go_ana 也应该拥有这些功能。

而是：

> **那些平台在承担“围棋平台”的职责；go_ana 应专门承担“个人实战学习系统”的职责。**

这是第一刀。

# 二、我建议把一级导航从 5 个页面继续砍到 3 个

你目前确定的是：

`首页 / 棋谱 / 复盘 / 复习 / 我的学习 + 设置`。

我现在建议进一步简化成：

| 一级入口 |       是否保留 | 说明                   |
| ---- | ---------: | -------------------- |
| 首页   |     **保留** | 所有下一步行动入口            |
| 棋谱   |     **保留** | 历史数据源                |
| 复盘   | **取消一级入口** | 选择某盘棋后进入，是工作空间，不是目的地 |
| 复习   |     **保留** | 今日训练                 |
| 我的学习 | **取消一级入口** | 合并进首页                |
| 设置   |    保留底部小入口 | 不占一级导航               |

最终左侧导航只有：

**首页**

**棋谱**

**复习**

下面单独一个：

**设置**

这会让整个软件一下安静很多。

# 三、为什么“复盘”反而不应该是一级导航

这听起来有点反直觉，但实际上很合理。

用户不会抽象地想：

> “我要进入复盘页面。”

真实意图通常是：

> “我要继续昨天那盘。”

或者：

> “我要复盘这一盘。”

所以复盘应该是一个 **Game Workspace**。

入口只有两个：

**首页 → 继续复盘**

或者：

**棋谱 → 选择棋局 → 开始复盘**

进入以后才出现棋盘、学习点、研究模式。

这样就不用解决一个荒唐的问题：

> 用户直接点击“复盘”，但系统不知道他到底要复盘哪盘棋，于是再让他选一遍。

软件特别喜欢制造这种自己发明出来的工作。

---

# 四、“我的学习”也应该从一级页面消失

这个页面的信息当然重要，但它不是一个高频“任务”。

用户每天真正需要知道的只有三个东西：

| 首页信息    | 回答的问题      |
| ------- | ---------- |
| 当前最重要问题 | 我最近到底该练什么？ |
| 今日复习    | 今天有什么要做？   |
| 最近趋势    | 我有没有改善？    |

例如：

**当前训练主题**

> 攻击前检查自身弱棋

**最近 30 盘**

> 此类错误：11盘 → 6盘 ↓45%

**今日复习**

> 6题 · 预计来自3类重复错误

到此其实已经完成了“我的学习”80%的作用。

原来规划的严重错误趋势、平均目损、重复错误率、主动纠正率、retention、transfer 等仍然应该存在。

但把它们移动到：

**首页 → 查看学习详情**

即可。

也就是说：

> **删除页面，不删除数据。**

这是后面整个减法项目最重要的原则。

---

# 五、后台可以复杂，前台必须简单

这是我认为 `go_ana` 下一版最值得建立的设计纪律。

后台继续拥有：

`KataGo`

`Human SL`

`LearningPriority`

`CandidateAssessment`

`EvidencePacket`

`LLM`

`SRS`

`Transfer Detection`

`Error Classification`

但用户不应该每天看到这些词。

用户只看到：

**为什么这一手值得学**

**重新下一次**

**这样好多了 / 仍然有问题**

**记住这一条原则**

**下次复习**

Human SL 尤其如此。

你已经确定 Human SL 的正确价值是比较当前棋力与高几级棋手的行为差异，并进入 `LearningPriority.level_gap`。

所以默认 UI 完全没有必要显示：

`humanPrior = 0.037`

应该翻译成：

> **这是一个很适合你当前阶段解决的问题。**

研究模式里再允许查看原始值。

# 六、现有功能我建议分成四档

这是整个减法方案真正执行时的核心。

| 功能                  | 决策          |    默认 UI | 原因                 |
| ------------------- | ----------- | -------: | ------------------ |
| SGF 导入              | **核心保留**    |       显示 | 学习数据入口             |

| 主动重下                | **核心保留**    |      强显示 | 第一核心交互             |
| CandidateAssessment | **核心保留**    |       转译 | 正确判题系统             |
| LLM 解释              | **核心保留**    |       简化 | 从 AI 数值到棋理         |

| Deep Verification   | 保留          |     高级菜单 | 很少需要               |
| Error Chain         | **撤出正式 UI** |      不显示 | 当前因果证据不足           |
| Learning Profile 大盘 | **合并**      |     首页详情 | 不需要一级页面            |
| 雷达图                 | **删除/暂停**   |      不显示 | 缺乏行动指导             |
| AI 棋力评分             | **弱化或删除**   |    不重点显示 | 与产品最终目标无关          |

| 独立 Learning Center  | **删除**      |      不存在 | 页面重复               |
| PDF 报告              | 降级          |     导出菜单 | 偶发行为               |
| 模型参数                | 降级          |     高级设置 | 普通用户不应关心           |
| AI 对弈               | **原则上不做**   |      不存在 | 星阵/OGS等做得更合适       |
| 通用死活题库              | **不做**      |      不存在 | 不属于本人实战学习          |
| 定式库                 | **不做**      |      不存在 | 产品边界扩张             |
| 社区功能                | **不做**      |      不存在 | 完全偏离核心             |

你原来的项目文档已经识别出问题：一条路径按 Point Loss 判断，另一条只有 AI 第一选算对，因此必须统一为 `Move → CandidateAssessment`。

这不是“低使用率功能优化”，这是逻辑上的重复功能，应直接删除。

# 七、复盘页面要进行第二轮大减法

你现有方向已经把“学习模式”和“研究模式”分开。

我赞同，但建议进一步收紧。

## 默认学习模式只允许出现六种信息

| 区域 | 内容                    |
| -- | --------------------- |
| 棋盘 | 当前局面                  |
| 问题 | 第 83 手 · 本盘第 2/5 个学习点 |
| 提问 | 如果重新下一次，你会怎么下？        |
| 判断 | 改正 / 改善 / 重复错误 / 合理替代 |
| 原因 | 一段核心解释                |
| 记忆 | 一条可迁移原则               |

不要同时出现：

胜率曲线、Ownership、Policy、Visits、10个候选、Human SL概率、大段 PV、模型参数。

即使这些数据很酷。数据库当然也觉得自己很酷，但没人会把 SQL 查询结果贴在首页。

# 八、LLM 解释也该做减法

你原设计要求模型输出七个结构：

发生了什么、问题在哪里、为什么实战容易这样想、更好的判断原则、当前水平合理选择、简短变化、记忆原则。

**数据结构保留七项，UI 不需要七项同时展开。**

默认压缩成：

| UI        | 来源                   |
| --------- | -------------------- |
| **问题在哪**  | 发生了什么 + 问题在哪里        |
| **应该怎么想** | 实战心理 + 判断原则 + 当前水平选择 |
| **记住一句**  | 记忆原则                 |

“查看变化”展开以后才展示简短变化。

“详细解释”展开以后再展示完整 EvidencePacket 解释。

这样既不破坏模型结构，又大幅降低阅读负担。

星阵 2026 年公开介绍其 AI 解说时，也明确指出传统 AI 分析存在“数值和变化图很多，但用户不知道到底错在哪里”的问题，同时承认语言模型在复杂局面中可能产生心理归因或局部判断偏差。([星阵围棋][3])

这反而更加支持你现在的架构：

> **KataGo 判事实，LLM 负责解释，而且解释必须尽量短。**

# 九、Learning Timeline 保留，因为它是真正差异化功能

这个我不建议砍。

你现在已经规定：

颜色 = 错误严重程度

紫色外圈/大小 = Learning Priority。

它能同时表达：

**大错但偶发**

和

**小错但总犯**

这正好把传统 AI Review 和 go_ana 区分开。

传统分析一般回答：

> 哪步亏得最多？

go_ana 应回答：

> **哪步最值得你学？**

因此 Timeline 留下。

但它只需要两套视觉编码。

不要以后又添加：

三角形 = recurrence
虚线 = Human SL
星星 = mastery
闪烁 = transfer
骷髅头 = blunder

最后棋谱时间轴会变成机场雷达。

# 十、Error Chain 暂时应该从产品里“消失”

这一刀我会砍得比较坚决。

你之前已经发现，目前 Error Chain 主要是启发式聚类，只凭时间距离、类别、同色等不能证明前一手“导致”后一手。

所以现在：

**后台实验可以留。**

**数据可以继续收。**

**正式 UI 不应该存在一个显眼的“错误链”功能。**

否则用户会把相关性理解成因果。

等未来真正加入：

棋块关系、Ownership 持续变化、空间关联、PV 强制关系等，再考虑重新上线。

这就是典型的：

> **功能没必要删除代码，但应该删除产品存在感。**

# 十一、错题库和复习必须合并

现在最容易发生产品膨胀的是：

MistakeBook

LearningEvent

Attempts

Mastery

Review

Training

Learning Profile

每一个数据概念最后都长成一个页面。

应该反过来。

用户只有一个概念：

> **复习**

进入之后只有：

| Tab | 内容                     |
| --- | ---------------------- |
| 今日  | 今天应该做的题                |
| 全部  | 来自历史实战的问题              |
| 已掌握 | retained / transferred |

甚至“历史作答”都不用独立 Tab。

点一道题 → 展开历史记录即可。

而后台仍然坚持：

> `LearningEvent = 唯一学习事实源`

MistakeBook 只是 View / SRS projection。

这样技术模型和用户心智都会统一。

---

# 十二、Retention 不需要成为“大功能”

Retention 很重要。

但大部分用户不会每天打开一个：

> “Retention Analytics Center”。

产品界真的很容易给一张折线图起一个英语名字，然后假装它值得一个页面。

实际上只需要在学习详情中显示：

**7日保留率 72%**

**30日保留率 61%**

以及：

**实战迁移**

> 最近 10 盘仅再次出现 1 次

即可。

而底层仍然严格区分：

Review failure

Training failure

Real-game recurrence

Transfer。

# 十三、首页应该成为整个系统的“任务调度器”

最终首页我建议只留下四张卡。

| 优先级 | 首页卡片       | 操作         |
| --: | ---------- | ---------- |
|   1 | **继续复盘**   | 继续昨天 2/5   |
|   2 | **今日复习**   | 开始 6 题     |
|   3 | **当前训练主题** | 攻击前检查自身弱棋  |
|   4 | **最近变化**   | 重复错误率 ↓18% |

然后一个非常弱的：

**查看学习详情**

就够了。

你原本首页已经是这个方向。

我建议不要再加：

总棋力
总对局
最近胜率
AI吻合度
本周时长
最高连胜
Radar
Achievement
每日格言

这些东西有一个共同特点：

**看起来像产品，实际上不告诉用户下一步干什么。**

# 十四、棋谱页也应该减

棋谱页真正的任务只有：

> **找到一盘棋并进入学习。**

所以表格核心列只需要：

| 字段    | 默认 |
| ----- | -: |
| 日期    |  √ |
| 对手    |  √ |
| 黑/白   |  √ |
| 结果    |  √ |
| 来源    |  √ |
| 复盘状态  |  √ |
| 学习问题数 |  √ |

像：

规则、贴目、时间设置、模型版本、分析深度等，

全部留在详情里。

过滤也先只保留：

**全部 / 未复盘 / 复盘中 / 完成**

再加搜索。

历史棋谱的数据模型当然继续完整保存日期、双方棋力、来源、时间设置、规则、贴目等。

这依旧是：

> 数据不减，界面减。

# 十五、研究模式不要删，但必须“藏深”

星阵和 KaTrain 说明专业研究能力确实有用户价值。星阵目前仍然强调胜率、子差等多角度分析；KaTrain 同样保留完整 KataGo 分析能力。([星阵围棋][4])

所以：

**Research Mode 不删。**

但它变成复盘右上角：

`学习 | 研究`

默认永远是：

`学习`

只有主动点击研究才显示：

Score

Winrate

Visits

候选

PV

Ownership

Policy

Human SL

Deep Verification

并且记住：

> 研究模式是工具箱，不是学习主路径。

---

# 十六、Human SL 应该成为“隐形超能力”

这个尤其值得强调。

未来优秀的 `go_ana` 不应该炫耀：

> 我支持 Human SL。

而应该悄悄利用 Human SL 得出：

> **“虽然只亏了 3.2 目，但这是你这个阶段特别值得解决的问题。”**

然后让这个点排进 Top 5。

用户完全没必要知道为什么后台用了：

current rank prior

stronger rank prior

level gap

除非进入研究模式。

KataGo 官方 Analysis Engine 已支持 Human SL，并将它定义为用于预测不同棋力人类玩家的着法及结果的人类监督学习模型。([GitHub][5])

你的使用方式恰好比“把 Human SL 作为另一个 AI 对手”更有产品价值。

---

# 十七、不要模仿涨棋网的“全家桶”

涨棋网目前已经覆盖 AI 分析、死活题、人机对战、不同算力报告、成长曲线等大量功能。([App Store][6])

它可以这么做，因为它的定位本身就是综合围棋训练平台。

而 `go_ana` 一旦开始加入：

通用死活题

AI 对战

定级

课程

排行榜

定式

社区

直播

棋友

就会失去最重要的差异：

> **所有学习内容都来自“我真正下过的棋”。**

所以以后新增功能应该继续使用你已经写好的那个判断标准：

> **它是否帮助用户发现问题、理解问题、训练问题，或者证明问题已经减少？**

我的建议甚至再加一道：

> **如果已有功能可以完成同一件事，不新增第二个入口。**

---

# 十八、真正删功能之前，要加一个极简 Usage Telemetry

这里必须谨慎一点。

目前我们有产品结构，但**没有真实用户行为数据**。

所以我不会装作知道：

> “Ownership 使用率只有 2.7%。”

这种数字如果没有埋点，就是产品经理占卜术。

建议先记录本地匿名事件，不需要复杂平台：

| Event                      | 用途          |
| -------------------------- | ----------- |
| `page_open`                | 页面真实使用频率    |
| `review_started`           | 复盘开始        |
| `learning_point_completed` | 学习点完成       |
| `retry_move`               | 主动重下        |
| `research_mode_opened`     | 研究模式使用率     |
| `ownership_enabled`        | Ownership需求 |
| `policy_enabled`           | Policy需求    |
| `deep_verify_used`         | 深度验证需求      |
| `practice_started`         | 复习启动        |
| `practice_completed`       | 复习完成        |
| `learning_details_opened`  | 学习详情需求      |
| `export_used`              | 导出需求        |

然后每个功能只问四个数字：

**Reach**

多少活跃用户碰过？

**Repeat**

碰过以后是否重复使用？

**Completion**

它是否帮助完成一次学习任务？

**Cost**

维护成本多高？

---

# 十九、我建议建立明确的“功能死亡标准”

一个功能如果同时满足以下条件中的 3 项，就应该被删、合并或降级：

1. 最近周期内很少被主动打开；
2. 使用者很少再次使用；
3. 不直接推进“复盘 → 重下 → 复习 → Transfer”；
4. 已有另一功能提供相同价值；
5. 维护成本或错误风险明显高；
6. 增加明显 UI 复杂度；
7. 用户不用它也不会影响学习结果。

尤其注意：

> **低频 ≠ 必须删除。**

例如“导入设置”可能很低频，但必不可少。

而：

> **高频 ≠ 必须保留。**

如果用户每天被迫点一个“确认”按钮，它使用率100%，但显然应该杀掉。

# 二十一、具体实施顺序

我不会先从删代码开始。那通常会制造另一种古老的人类娱乐项目，叫“删完发现别处还引用”。

| Release | 工作                                |
| ------- | --------------------------------- |
| **R0**  | 建立功能清单 + 使用事件埋点                   |
| **R1**  | 一级导航减为：首页 / 棋谱 / 复习               |
| **R2**  | “我的学习”合并进首页                       |
| **R3**  | 复盘移出一级导航，改成 Game Workspace        |
| **R4**  | 学习模式默认隐藏所有专业指标                    |
| **R5**  | 统一 CandidateAssessment，删除 A/B/C/D |
| **R6**  | MistakeBook UI 与复习合并              |
| **R7**  | Error Chain 撤出正式 UI               |
| **R8**  | Human SL 完全后台化                    |
| **R9**  | 研究模式集中收纳所有高级能力                    |
| **R10** | 根据实际埋点删除长期无人使用的代码路径               |

其中 **R5 以前的 P0 逻辑问题仍然必须优先**。例如 LearningEvent 全量入库、recurrence 按 `game_id`、Human SL 真正接入 LearningPriority、retention/transfer 语义等，本来就是当前最高优先级。

# 二十二、做完这轮减法以后，验收标准也应该改变

不要验收：

> “我们现在还有多少功能。”

应该验收：

| 场景       | 标准                               |
| -------- | -------------------------------- |
| 打开 App   | 5 秒知道今天干什么                       |
| 导入棋谱     | 很快进入分析                           |
| 打开历史棋    | 直接开始复盘                           |
| 进入学习点    | 看不到 AI 答案                        |
| 重下一手     | 立即知道改善程度                         |
| 看解释      | 30 秒能提炼一条原则                      |
| 完成复盘     | 自动进入未来复习                         |
| 再次打开 App | 今日任务自动出现                         |
| 过几盘棋     | 能知道错误是否真的减少                      |
| 普通使用     | 不需要理解 Visits / Policy / Human SL |

你原有的 UI 验收标准已经要求首页 5 秒知道下一步、复盘默认隐藏 AI、研究模式快速找到候选和目差等。

现在可以进一步统一成一个指标：

> **用户完成一次完整学习闭环，需要做多少次选择？**

这个数字越低，产品越好。

# 最终我建议砍成一句产品定义

旧思维可能是：

> **“这是一个拥有 KataGo、Human SL、LLM、错题、画像、研究等很多功能的围棋工具。”**

做完减法后应该变成：

> **“导入自己的棋，系统每天只告诉你最值得改的几个问题，并持续检查你后来到底改掉没有。”**

后台可以比现在复杂两倍。

**前台应该比现在简单一半。**

这才是 `go_ana` 值得走的方向。AI Sensei 已经证明“从自己的问题进入训练”是非常自然的闭环；KaTrain 证明 Point Loss + Retry 足以形成强复盘体验；星阵证明专业研究可以很深，但不意味着所有专业数据都该成为学习主界面。([AI Sensei][1])

下一阶段真正值得做的不是继续设计新页面，而是按照上面这张表，对现有 `go_ana` **逐功能做一次 Keep / Merge / Hide / Delete 审计**。这会比再加十个新功能更接近一个成熟产品。
