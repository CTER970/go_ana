# 一、P0：`best_prior` 读取字段写错了

这是基础错误，而且之前没有抓出来。

`review.py` 当前写的是：

```python
best_prior = _num(best, "policy")
```



但 KataGo Analysis Engine 的 `moveInfos` 字段名称明确是：

```text
prior
```

不是 `policy`。([GitHub][3])

项目另一个模块 `problem_drill.py` 反而写对了：

```python
best_policy = float(_num(best_info, "prior", 0.0))
```



### 后果

由于 `_num(..., default=0)`，当前 `MoveEvaluation.best_prior` 很可能长期等于：

```text
0.0
```

然后它又被送入：

```python
difficulty_of(e.best_prior)
```

计算单局平均“难度”。

所以目前以下指标可能系统性偏向“这手很冷门/很难”：

* `avg_difficulty`
* 一部分单局表现相关解释
* 任何消费 `MoveEvaluation.best_prior` 的功能

### 修复

直接改：

```python
best_prior = _num(best, "prior", None)
```

而且**缺失时应该是 `None`，不要默认0**。

这是第一优先级。

---

# 二、P0：榜外选点 `allowMoves` 请求格式不符合 KataGo 协议

这是这次审查发现的最实质性的运行时 bug。

当前：

```python
def forced_move_query(query, move):
    q = dict(query or {})
    q["allowMoves"] = [str(move)]
    return q
```



例如实际发：

```json
"allowMoves": ["Q10"]
```

但 KataGo Analysis Engine 明确要求：

```text
allowMoves = list of dicts
```

每个 dict 必须包含：

* `player`
* `moves`
* `untilDepth`

([GitHub][3])

也就是说应该类似：

```python
def forced_move_query(query, move, player):
    q = dict(query or {})
    q["allowMoves"] = [{
        "player": player,
        "moves": [move],
        "untilDepth": 1,
    }]
    return q
```

这里 `untilDepth=1` 很重要：

> 只强制根节点第一手是用户选择，后面的变化重新自由搜索。

当前 app 又直接调用这个错误结构：

```python
q = forced_move_query(..., coord)
self.client.analyze(q)
```



### 后果

README 当前最重要的卖点之一：

> “榜外选点也会自动送 KataGo 强制分析”

实际上很可能在真实 KataGo IPC 中报解析错误。

这类问题纯 Python 单元测试完全可能测不出来。

### 必须增加一个真实 KataGo Integration Test

不要只测试：

```python
assert q["allowMoves"]...
```

而应该真的送给 KataGo：

> 用户下一手不在 moveInfos → 强制分析 → 返回该手 scoreLead → CandidateAssessment 正常完成。

# 三、P0：长期 LearningEvent 仍然只保存“每盘目损 Top5”

这是当前学习系统最大的结构问题。

`learning_store.sync_profile_summary()` 仍然：

```python
for problem in summary.get("top_problem_moves") or []:
```



也就是说：

> LearningEvent 数据库并不是“用户所有值得学习的历史错误”。

而是：

> **每盘先按旧逻辑筛出来的 Top Problem。**

这和 LearningPriority 的设计目标发生根本冲突。

举例：

一盘有：

* 20目偶发对杀错误
* 15目偶发计算错误
* 10目死活
* 8目官子
* 7目方向
* **4目自动跟应**

那个4目自动跟应不会进 LearningEvent。

连续20盘都是如此。

于是系统永远不知道：

> 你其实已经连续20盘犯“自动跟应”。

### 正确架构

应该彻底分成：

```text
AnalysisProblemEvent
        ↓
所有达到最低学习阈值的问题全部保存
        ↓
历史复发/掌握/HumanSL
        ↓
LearningPriority
        ↓
SelectedLearningProblem
        ↓
UI只展示Top5
```

**Top5只能是显示结果，绝不能是数据库入口。**

这个必须改。

# 四、P0：复发次数仍然不是“出现过多少盘”

当前：

```python
for evt in store_events:
    ...
    index[category] += 1
```



函数文档却写：

> `{primary_category: 出现盘数}`

我用当前源码直接做了一个逻辑验证：

```text
g1：attack_defense 2个事件
g2：attack_defense 1个事件
```

当前结果：

```text
attack_defense = 3
```

正确应该是：

```text
attack_defense = 2盘

index = {}

for evt in events:

return {
    category: len(game_ids)
    for category, game_ids in index.items()
}
```

最好以后同时保存两种指标：

```text
event_count
game_count
```

例如：

> 攻防错误：14次 / 8盘

两个都有价值。

但绝对不能混为一个指标。

# 五、P0：现在有两套互相矛盾的“答对”标准

后面加入：

* 棋盘空间位置；
* 同一棋块；
* ownership连续变化；
* PV强制关系；

以后再提高因果置信度。

# 二十一、还有一个非常现实的筛选问题：2目以下的问题永远没资格参加 LearningPriority

`problem_drill` 进入排序前先：

```python
e.loss >= threshold
```

默认threshold：

> 2目。



所以：

> 一个连续20盘都犯、每次亏1.8目的错误

永远不会进入学习排序。

对普通AI复盘没问题。

但对个人长期学习：

> 不合理。

建议把两个阈值拆开：

### Event Eligibility

例如：

```text
≥1.0 / 1.5目
```

或者 Human SL/高复发也允许进入。

### Single-game Highlight

例如：

```text
≥2.0目
```

这样：

> 小但反复的问题能够进入长期数据库，

但不会每盘都打扰用户。

# 二十四、这一轮必须增加的回归测试

我建议至少增加这 12 个测试。否则很容易修完又复发，软件开发最稳定的传统之一就是把同一 bug 修三遍。

1. `moveInfo["prior"]` 能正确进入 `MoveEvaluation.best_prior`
2. `allowMoves` 请求通过真实 KataGo Analysis Engine
3. 同一盘3个同类事件，recurrence game count只能+1
4. 每盘第6大的错误仍能进入 LearningEvent
5. 删除一盘历史棋后 recurrence 能下降
6. 字母选择Q11和棋盘点击Q11必须得到完全相同判定
7. 第4选亏0.4目必须判合理
8. 第2选亏5目必须判问题
9. Human Model关闭时 `humanPrior=None`，不得回退普通prior
10. Human Model开启时 current/stronger profile 真正改变 LearningPriority
11. 阶段训练失败不得被标记为 real-game recurrence
12. “延迟保留”必须跨越指定时间间隔

再增加两个 Golden Test：

```text
同一个SGF
同一个KataGo模型
同样visits
```

应产生稳定：

> 问题事件集合

以及大体稳定：

> Top5学习节点。

## 这一轮最重要的结论

项目现在最危险的不是：

> 某个按钮不好看。

而是：

> **很多模块已经拥有正确的名字，但少数数据还没有真正拥有那个名字所代表的语义。**

比如：

* recurrence 还不是盘数；
* retention 还不是真延迟；
* transfer 还不是真迁移；
* Human SL 还没真正参与排序；
* complexity 还没有真正参与判题；
* game importance 还没真正参与优先级；
* 九类 taxonomy 还没有九类可靠识别。

这其实是一个好阶段。说明产品结构已经基本确定，现在进入的是更困难但更有价值的阶段：

> **让每一个指标都真的可信。**

这轮我会把 **`prior字段 → allowMoves → LearningEvent全量入库 → recurrence按盘 → CandidateAssessment单一判分源 → mastery单一事实源`** 定为第一批修复范围。在这六件事解决之前，我不建议再增加任何新的产品功能。
